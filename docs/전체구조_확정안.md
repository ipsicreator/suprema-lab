# 수프리마랩 전체 구조 확정안

기준일: 2026-11-13 / 상태: 설계 기준 확정, 구현·검증 상태 별도 관리

수프리마랩은 본사가 공통 입시 근거와 운영 정책을 관리하고, 학원별 담당 컨설턴트가 배정 학생을 상담하는 서비스다. 기존 진단·탐구·보고서 자산은 검증하여 재사용한다. 전체 프로젝트 폐기와 재개발은 채택하지 않는다.

## 1. 운영 구조와 용어

**마스터 → 본사 관리자 → 학원 → 담당 컨설턴트 → 배정 학생**

학원은 조직이며 계정 역할이 아니다. 학원 운영 책임자는 **학원 관리자**, 학생 업무 실행자는 **담당 컨설턴트**로 부른다. ‘멘토’는 과거 서비스명에 사용된 표현으로, 별도 권한 역할로 만들지 않는다. 한 사용자가 학원 관리자와 컨설턴트를 겸할 수 있으므로 사용자·소속·역할을 별도 관계로 관리한다.

| 역할 | 관리 범위 | 허용할 핵심 업무 |
|---|---|---|
| 마스터 | 플랫폼 전체 | 본사 관리자 지정, 권한·가격 정책, 공통 근거·판단 기준 승인 |
| 본사 관리자 | 배정 학원 | 학원 등록·운영 지원, 계약·이용권·사용량 관리 |
| 학원 관리자 | 소속 학원 | 컨설턴트 초대·해제, 학생 등록·담당 배정, 결과 검토 |
| 담당 컨설턴트 | 배정 학생 | 자료 확인, 진단·탐구·상담, 보고서 작성·확정 |
| 학생·학부모 | 본인에게 공개된 결과 | 결과 열람·수신. 직접 실행은 별도 후속 범위 |

계정에 저장된 역할과 소속을 서버에서 판정한다. 학원명·학생 학교명·이름 입력값은 권한 근거로 사용하지 않는다. 타 학원 자료 접근과 미배정 학생 조회는 서버 및 데이터 저장소에서 거부한다. 본사 관리자의 학생 원문 접근도 업무에 필요한 권한으로 별도 제한한다.

## 2. 앱 모듈과 경로

| 모듈 | 현재 경로·소스 | 구조 기준 |
|---|---|---|
| 소개·진입 | `/intro`, `/diagnosis` | 서비스 소개와 학생별 업무 진입 |
| 학생별 실행 | `/diagnosis/step1`~`step4` | 정보·자료 → 분석 → 탐구·독서·세특 → 입시 위치 진단 |
| 탐구·코칭 | `/exploration`, `/setuk`, `/api/solution` | 실제 활동과 근거를 바탕으로 초안을 제안하고 담당자가 검토 |
| 보고서 | `/report`, `/api/send-email` | 확정 결과만 출력·전달하고 입력·근거·작성자를 추적 |
| 관리자 | `/admin`, `/admin/admissions`, `/admin/pricing` | 입시 근거 버전 관리와 가격·결제 운영 |
| 공통 입시 근거 | `lib/admissions`, `/api/admissions` | 관리자 반영 버전을 공통 조회 |
| 수치 진단 | `lib/utils/admission`, `/api/diagnosis` | 입력과 비교 근거를 검증하여 재현 가능한 규칙으로 판단 |
| 인증·현재 사용자 | `auth.ts`, `src/lib/server-auth.ts` | 로그인과 서버 권한 판정 |
| 운영 정보 | `src/lib/platform-store.ts` | 프로필·이용권·주문·사용량. 영구 저장 구조 전환 대상 |
| 기타 진단 | `/ipsidna-prism` | 현재 분리된 기능을 유지하고 학생 소속·배정 체계와 후속 연결 |

화면은 서버가 검증한 데이터를 표시한다. 진단 결과를 미리 정해 둔 대학명·판정으로 채우지 않는다. 데이터가 없거나 비교 근거가 부족하면 ‘판단 보류’로 표시한다. API가 실패한 결과를 정상 결과처럼 출력·발송하지 않는다.

## 3. 데이터 소유와 저장 기준

| 데이터 | 소유 범위 | 저장·연결 원칙 |
|---|---|---|
| 대학·학과·전형·입결·출처 | 본사 공통 | 학년도·캠퍼스·전형·지표를 구분하고 승인 버전 보존 |
| 학원·계약·이용권 | 본사 및 해당 학원 | `academyId`로 식별. 학교명과 분리 |
| 사용자·소속·역할 | 플랫폼 및 해당 조직 | 사용자 ID, 소속 관계, 역할을 분리 |
| 학생·담당 배정 | 해당 학원 | 학생 ID·학원 ID·담당자 ID·배정 기간 연결 |
| 분석·진단·상담·보고서 | 해당 학원·배정 학생 | 작성자·입력·근거 버전·확정 상태 연결 |
| 변경·공개·내보내기 이력 | 권한 있는 운영자 | 변경자·시각·이전 상태·대상 보존 |

배포 구조는 **GitHub → Vercel의 Next.js 앱 → 서버 API → PocketBase 영구 저장소**를 기준으로 한다. 비밀값은 서버 환경변수로만 관리한다. 운영 데이터는 Vercel 실행 파일시스템에 쓰지 않는다. 로컬 개발용 파일 저장은 운영용 영구 저장과 구분한다.

확정 보고서는 당시 입력값·입결 데이터 버전·판단 기준 버전을 고정한다. 공통 입결이 갱신되어도 이미 확정된 보고서의 근거가 바뀌지 않도록 한다.

## 4. 관리자 파일 반영 구조

**파일 선택 → 브라우저 해석 → 시트 선택 → 압축 전송 → 서버 검증·임시 저장 → 미리보기 → 명시적 전체 반영 → 활성 버전 전환**

- 지원 형식: `.xlsx`, `.xls`, `.csv`, `.tsv`.
- 현재 한도: 원본 20MB, 최대 50,000행, 압축 전송 3MB. 실제 열 제목을 첫 30행에서 찾는다.
- 대학·모집단위·전형유형·전형명은 필수다. 빈 데이터와 잘못된 필수 항목은 반영을 막는다.
- 평균·50%컷·70%컷·등급·환산점수를 혼합하지 않는다. 복합 값과 범위 밖 값은 원문을 보존하고 수치 비교에서 제외하거나 검증 오류로 알린다.
- 선택한 한 시트가 공통 데이터 전체를 교체한다. 여러 파일 병합은 현재 기능에 포함하지 않는다.
- 임시 저장은 서비스 데이터를 바꾸지 않는다. 반영 시 활성 포인터 하나를 전환하며 이전 버전은 보존한다.
- PocketBase의 `suprema_admission_revisions`는 비공개 압축 스냅샷, `suprema_admission_active`는 활성 버전과 최근 반영 이력을 저장한다.
- 서비스 조회도 압축 응답을 사용한다. 새로 연 진단 화면과 진단 API는 같은 활성 버전을 읽는다. 이미 열린 화면은 새로고침한다.
- 로컬 `.cache/admissions`는 개발용이며 Git·배포 대상에서 제외한다. Vercel에서 영구 저장소가 없으면 반영·복원을 차단한다.

사용 절차와 설정은 [관리자 입시 데이터 업로드](관리자_입시데이터_업로드.md)를 따른다.

## 5. 구현 범위와 남은 차이

| 구분 | 확인 상태 | 완료로 보지 않는 범위 |
|---|---|---|
| 관리자 파일 반영 | 업로드·검증·임시 저장·반영·복원 및 서비스 공통 조회 코드 존재 | 실제 운영 환경 설정과 운영 데이터 반영은 별도 |
| 현재 관리자 권한 | 로그인 세션과 `ADMIN_EMAILS` 목록 기반 서버 검사 | 마스터·본사·학원·컨설턴트의 전체 역할 권한 체계는 미구현 |
| 학원별 구분·학생 배정 | 이 문서의 설계 기준 확정 | 학원별 접근 분리, 계정 소속, 담당 배정의 실제 구현·검증 필요 |
| 운영 정보 저장 | `src/lib/platform-store.ts`가 로컬 JSON 파일에 기록 | Vercel 영구 저장·동시 수정·학원별 구분을 보장하지 못함 |
| 학생별 실행·진단 | 화면·API·계산 모듈 존재. 이번 점검에서 실제 값 연결과 오류 사례를 검증 | 외부 AI·메일·운영 DB의 실제 동작은 설정별 검증 필요 |
| 입시 기본 자료 | 번들 JSON은 초기 조사에서 26,411개 빈 레코드로 확인됨 | 원본 엑셀 부재와 다름. 관리자 반영 버전과 혼동하지 않음 |

V7.24 원본은 프로젝트 밖의 바탕화면 `수시` 폴더에 보존되어 있다. 새 반영 기능의 시험은 별도 저장 경로를 사용한다. 원본 전체를 운영 데이터에 게시하거나 외부 서비스에 배포한 것으로 간주하지 않는다.

## 6. 완료 판정과 다음 작업 순서

1. **현재 앱 회귀 검증:** 빌드·타입 검사·정적 검사, 관리자 업로드/복원, 진단 입력 오류·근거 없음·연도 누락, 주요 화면의 실제 데이터 연결을 확인한다. 확인 결과는 검증 보고서로 분리한다.
2. **학원 운영 기반 구현:** 계정·소속·역할·학생·배정 관계를 구현하고, 서로 다른 두 학원과 여러 담당자로 교차 조회가 거부되는지 검증한다.
3. **운영 저장소 통합:** 프로필·이용권·주문·사용량을 영구 저장소로 전환하고 재시작·동시 수정·복구를 검증한다.
4. **확정 보고서 추적:** 보고서에 입력·입결 버전·판단 기준·작성자·공개 상태를 연결한다.
5. **배포 검증:** Vercel 환경변수, PocketBase 접근·비공개 규칙, 로그인 제공자, AI·메일·결제 설정을 확인한 뒤 승인된 배포를 수행한다.

설계 확정, 로컬 검증 통과, 운영 적용 완료는 서로 다른 상태로 기록한다. 학원별 권한과 영구 운영 저장이 검증되기 전에는 다학원 운영 체계가 완성되었다고 표시하지 않는다.

## 7. 외부 설정 확인 항목

| 항목 | 확인할 설정 |
|---|---|
| 관리자 로그인 | `AUTH_SECRET` 또는 `NEXTAUTH_SECRET`, 로그인 제공자 설정, `ADMIN_EMAILS` |
| 공통 입결 영구 저장 | `PB_URL` 또는 `NEXT_PUBLIC_PB_URL`, `PB_ADMIN_EMAIL`, `PB_ADMIN_PASSWORD` |
| AI·메일·결제 | 각 기능의 서버 API 키·발신 설정·결제 검증 설정. 비밀값은 문서에 기록하지 않음 |
| 대학어디가 | 공식 외부 API 명세·제공 범위·이용 조건 확보 후 연계 결정. 미확인 내부 호출을 공식 연동으로 사용하지 않음 |
| 운영 반영 | GitHub·Vercel 프로젝트 연결, 대상 브랜치·환경, 복구 가능한 이전 배포 확인 |

이 문서는 전체 구조의 기준 문서다. 사업 목적과 세부 기획 이력은 [통합 기획안](../수프리마랩_통합기획안.md)에 보존하며, 충돌하는 구조·용어·구현 상태는 이 문서를 우선한다.

최신 로컬 검증 결과는 [앱 점검·수정 결과](2026-11-13_앱점검_수정결과.md)를 따른다.
